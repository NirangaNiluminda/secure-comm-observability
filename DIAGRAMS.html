Authentication Flow — Register & Login

How user credentials are created and verified. Passwords are NEVER stored in plain text — only a bcrypt hash (60 bytes, salt embedded). JWT tokens are stateless and scoped.

sequenceDiagram
    participant BR as Browser
    participant API as Flask  /api
    participant DB as SQLite  users.db
    participant JWT as JWT  HS256

    rect rgb(15, 40, 80)
        Note over BR,DB: ── REGISTRATION ──
        BR->>API: POST /api/register  {username, password}
        API->>API: Validate: len ≥ 3, pw len ≥ 6
        API->>API: hashed = bcrypt.hashpw(pw, gensalt(rounds=12))
        Note over API: ~150ms intentionally — brute force defence
        API->>DB: INSERT INTO users (username, hashed_password)
        DB-->>API: OK  (IntegrityError if username taken)
        API->>API: _append_audit_log("account_created")
        API-->>BR: 201 Created  {success: true}
    end

    rect rgb(10, 50, 30)
        Note over BR,JWT: ── LOGIN ──
        BR->>API: POST /api/login  {username, password}
        API->>API: _check_rate_limit("login", ip, 15)
        Note over API: ⚡ Rate limit: 15 attempts per 60s per IP
        API->>DB: SELECT * FROM users WHERE username = ?
        alt user not found
            API->>API: bcrypt.checkpw(dummy, dummy_hash)
            Note over API: Dummy check: same timing as real check
            Note over API: Prevents user enumeration attack
            API-->>BR: 401 Invalid username or password
        else user exists
            API->>API: bcrypt.checkpw(password, stored_hash)
            alt password wrong
                API->>API: _append_audit_log("login_failed")
                API-->>BR: 401 Invalid username or password
            else password correct
                API->>JWT: jwt.encode({username, scopes, exp=+60min})
                JWT-->>API: signed HS256 token
                API->>API: _append_audit_log("login_success")
                API-->>BR: 200  {token, username}
                Note over BR: Token stored in React state (memory only)
                Note over BR: Private key NEVER leaves browser
            end
        end
    end
bcrypt Work Factor

Cost factor 12 makes each hash ~100–150ms. Guessing 1 million passwords takes ~28 hours per CPU core.

Timing Attack Prevention

Even for non-existent users, a dummy bcrypt check runs — so attacker cannot tell if a username exists by timing the response.

JWT Scopes

Token carries scopes: chat:send · chat:read · key:read. Each endpoint checks the required scope before acting.

Rate Limiting

15 login attempts per 60-second window per IP. The 16th attempt returns HTTP 429 Too Many Requests.

ECDH P-256 Key Exchange — Perfect Forward Secrecy

Both Alice and Bob generate fresh ephemeral EC key pairs every session (every page load). The shared AES key is DERIVED — never transmitted. This is called Perfect Forward Secrecy (PFS): even if a key is stolen later, past messages cannot be decrypted.

sequenceDiagram
    participant A as Alice  (Browser)
    participant S as Server  (users{})
    participant B as Bob  (Browser)

    rect rgb(20, 30, 80)
        Note over A,S: ── On Login: Alice registers her public keys ──
        A->>A: ecdhA  = generateECDHKeyPair()   P-256
        A->>A: ecdsaA = generateECDSAKeyPair()  P-256
        Note over A: Private keys stay in browser memory (never sent)
        A->>S: socket.register(jwt, ecdhA.pub, ecdsaA.pub)
        S->>S: users["alice"] = { ecdhA.pub, ecdsaA.pub, sid }
    end

    rect rgb(20, 30, 80)
        Note over B,S: ── On Login: Bob registers his public keys ──
        B->>B: ecdhB  = generateECDHKeyPair()   P-256
        B->>B: ecdsaB = generateECDSAKeyPair()  P-256
        B->>S: socket.register(jwt, ecdhB.pub, ecdsaB.pub)
        S->>S: users["bob"] = { ecdhB.pub, ecdsaB.pub, sid }
    end

    rect rgb(10, 50, 30)
        Note over A,B: ── Key Derivation: Alice opens chat with Bob ──
        A->>S: get_public_key("Bob")  [requires JWT scope: key:read]
        S-->>A: { ecdhB.pub, ecdsaB.pub }

        A->>A: shared_secret = ECDH(ecdhA.priv, ecdhB.pub)
        A->>A: aes_key = HKDF-SHA256(shared_secret, 32 bytes)
        Note over A: aes_key is the AES-256-GCM encryption key

        Note over B: When Bob opens chat with Alice...
        B->>S: get_public_key("Alice")
        S-->>B: { ecdhA.pub, ecdsaA.pub }

        B->>B: shared_secret = ECDH(ecdhB.priv, ecdhA.pub)
        B->>B: aes_key = HKDF-SHA256(shared_secret, 32 bytes)
        Note over A,B: ✓ Alice and Bob hold IDENTICAL aes_key
        Note over A,B: ✓ Key was NEVER transmitted — PFS achieved
    end
Why ECDH Works

ECDH(Alice_priv, Bob_pub) = ECDH(Bob_priv, Alice_pub) — this is the mathematical property of elliptic curves. Both sides get the same point on the curve, which is then hashed into an AES key.

Perfect Forward Secrecy

Ephemeral keys (new keypair each login) mean: if an attacker records encrypted traffic today and steals a key tomorrow, they CANNOT decrypt past sessions.

HKDF-SHA256

The raw ECDH shared secret is passed through HKDF (HMAC-based Key Derivation Function) to produce a uniformly random 256-bit AES key, with domain separation info string.

P-256 Key Size

256-bit elliptic curve key provides ~128-bit security strength — equivalent to 3072-bit RSA, but with much smaller keys and faster computation.

End-to-End Encrypted Message Flow

Complete lifecycle of a single message. The server performs 4 security checks before forwarding but never sees the plaintext. The receiver runs 5 independent verifications before displaying the message.

sequenceDiagram
    participant A as Alice  (Browser)
    participant S as Server  (4 checks)
    participant B as Bob  (Browser)

    Note over A: ── Message Preparation (all crypto in browser) ──
    A->>A: ① hash = SHA-256(plaintext)
    A->>A: ② iv   = crypto.getRandomValues(12 bytes)
    A->>A: ③ ciphertext = AES-256-GCM(aes_key, iv, plaintext)
    A->>A: ④ msgId = crypto.randomUUID()
    A->>A: ⑤ envelope = JSON{from,to,msgId,sentAt,iv,ciphertext,hash}
    A->>A: ⑥ signature = ECDSA-sign(ecdsaA.priv, envelope)

    A->>S: socket.send_message {from,to,ciphertext,iv,signature,hash,msgId,sentAt,token}

    rect rgb(20,40,20)
        Note over S: ── Server: 4 Security Checks (NO decryption) ──
        S->>S: ① JWT verify scope "chat:send"
        S->>S: ② rate_limit("send", alice, limit=120/60s)
        S->>S: ③ msgKey = "alice:msgId"  →  msgKey ∉ seen_message_ids
        Note over S: Replay attack blocked if msgId already seen
        S->>S: ④ ECDSA verify(alice_registered_ecdsa_pub, signature, envelope)
        Note over S: InvalidSignature raised if tampered or MITM
        S->>S: seen_message_ids.add(msgKey)
        S->>S: _append_audit_log("message_sent", {from,to,msgId,hash})
        Note over S: Server logs ONLY metadata — never the plaintext or ciphertext
        S-->>B: socket.receive_message {ciphertext,iv,signature,hash,msgId,sentAt}
    end

    rect rgb(20,30,60)
        Note over B: ── Bob: 5 Independent Verifications ──
        B->>B: ① seenIds.has("alice:msgId") → false → add to set
        Note over B: Client-side replay protection (dedup set)
        B->>B: ② |Date.now() - sentAt| < 5 minutes
        Note over B: Stale message rejection (timestamp window)
        B->>B: ③ ECDSA verify(aliceEcdsaPub, signature, envelope)
        Note over B: InvalidSignature if message tampered in transit
        B->>B: ④ plaintext = AES-256-GCM-decrypt(aes_key, iv, ciphertext)
        Note over B: InvalidTag exception if any ciphertext byte changed
        B->>B: ⑤ SHA-256(plaintext) === hash
        Note over B: Final integrity check on decrypted content
        B->>B: ✓ Display message with "Verified" badge
    end
True E2EE

The server receives only encrypted blobs {ciphertext, iv, signature, hash}. It cannot decrypt the content. Even database or server compromise reveals nothing about message content.

Multi-Layer Integrity

Three independent integrity checks: AES-GCM auth tag (ciphertext level), ECDSA signature (envelope level), SHA-256 hash (plaintext level). All three must pass.

Signed Envelope

The ECDSA signature covers ALL fields: from, to, msgId, sentAt, iv, ciphertext, hash. Changing any single field invalidates the signature.

Non-Repudiation

Alice's ECDSA private key signs every message. Alice cannot later deny sending it. The audit log records the signature was verified, creating a cryptographic proof of authorship.

Attack 1 — Replay Attack

STRIDE: Spoofing / Repudiation  Attacker captures a legitimate encrypted message and re-sends the exact same packet later, hoping the server processes it twice (e.g., double payment, duplicate command).

sequenceDiagram
    participant A as Alice  (Sender)
    participant ATK as Attacker  (MITM)
    participant S as Server
    participant B as Bob  (Receiver)

    Note over A,B: ── PHASE 1: Legitimate first delivery ──
    A->>ATK: send_message {msgId:"abc-123", ciphertext:"...", sig:"..."}
    Note over ATK: Attacker intercepts and RECORDS the packet
    ATK->>S: (forwards) send_message {msgId:"abc-123", ...}
    S->>S: ✓ "alice:abc-123" not in seen_message_ids → ALLOW
    S->>S: seen_message_ids.add("alice:abc-123")
    S-->>B: receive_message {msgId:"abc-123", ...}
    B->>B: ① seenIds.add("alice:abc-123")
    B->>B: ② Timestamp OK — recent message
    B->>B: ③ ECDSA verify → valid
    B->>B: ④ AES-GCM decrypt → success
    B->>B: ✓ Displays message

    Note over ATK: ── PHASE 2: Replay Attack (same packet re-sent) ──
    ATK->>S: REPLAY send_message {msgId:"abc-123", ...}
    Note over S: 🛡️ SERVER DEFENSE — seen_message_ids check
    S->>S: "alice:abc-123" IN seen_message_ids → BLOCKED
    S->>S: _append_audit_log("attack_replay_blocked")
    S-->>ATK: delivery_error "Replay attack detected: duplicate message_id"

    Note over B: 🛡️ CLIENT DEFENSE (backup — even if server missed it)
    Note over B: seenIds.has("alice:abc-123") → true → silently dropped
    Note over B: Also: timestamp 400s old → > 5 min window → rejected
Attack Vector

Record any valid WebSocket packet. Re-transmit it later with zero modification. No crypto knowledge required — the attacker is just resending a valid captured packet.

Primary Defense

Server-side seen_message_ids set tracks every (from, msgId) pair. Duplicates are blocked at the server before reaching the recipient.

Secondary Defense

Client-side seenIdsRef Set provides a second deduplication layer. Even if the server missed it, the browser would silently discard the duplicate.

Tertiary Defense

5-minute timestamp window: |Date.now() - sent_at| < 300,000 ms. Messages older than 5 minutes are automatically rejected, regardless of msgId.

Attack 2 — Ciphertext Tampering

STRIDE: Tampering / Information Disclosure  A Man-in-the-Middle flips bits in the encrypted message hoping to alter what Bob reads, or to confuse the decryption process.

sequenceDiagram
    participant A as Alice  (Browser)
    participant ATK as Attacker  (MITM)
    participant S as Server
    participant B as Bob  (Browser)

    Note over A: ── Alice encrypts and signs ──
    A->>A: ciphertext = AES-256-GCM(aes_key, iv, "Hello Bob!")
    A->>A: envelope = JSON{..., iv, ciphertext, hash}
    A->>A: signature = ECDSA-sign(alice_priv, envelope)
    A->>ATK: send_message {ciphertext, iv, signature, hash}

    rect rgb(80,20,20)
        Note over ATK: 🔴 ATTACK — flip one byte of ciphertext
        ATK->>ATK: corrupted_ct = ciphertext[0] XOR 0xFF
        Note over ATK: Attacker does NOT have Alice's ECDSA private key
        Note over ATK: Cannot re-sign the modified envelope
        ATK->>S: send_message {corrupted_ct, iv, signature, hash}
    end

    rect rgb(20,60,20)
        Note over S: 🛡️ DEFENSE LAYER 1 — ECDSA Signature Verification
        S->>S: rebuild envelope with corrupted_ct
        S->>S: ECDSA verify(alice_pub, signature, envelope_with_corrupted_ct)
        S->>S: ✗ RAISES InvalidSignature!
        Note over S: Original sig covers original ct, not corrupted ct
        S->>S: _append_audit_log("message_rejected", reason="sig_fail")
        S-->>ATK: delivery_error "Signature verification failed"
    end

    Note over B: 🛡️ DEFENSE LAYER 2 (client — if message somehow forwarded)
    B->>B: AES-256-GCM decrypt(aes_key, iv, corrupted_ct)
    B->>B: ✗ RAISES InvalidTag! (GCM auth tag mismatch)
    B->>B: Show: ⚠ Verification failed: AES-GCM integrity check failed

    Note over B: 🛡️ DEFENSE LAYER 3 — SHA-256 Hash
    B->>B: SHA-256(decrypted_plaintext) ≠ hash → tamper confirmed
Why It Fails (Layer 1)

The ECDSA signature covers the ciphertext as a field in the envelope. Changing the ciphertext = changing the signed data = signature mismatch. Attacker cannot forge a new signature without Alice's private key.

Why It Fails (Layer 2)

AES-256-GCM is an AEAD cipher. It appends a 16-byte authentication tag that binds the key, IV, and ciphertext together. Any modification to ciphertext bytes invalidates this tag — InvalidTag is raised.

Chat UI Demo

Enable "Tamper Attack Demo" toggle → send a message → Alice's browser corrupts ciphertext locally → Bob sees ⚠ in red. This tests the AES-GCM layer since the tampered ct is signed (simulating a self-tampering scenario).

Real Simulator

The attack simulator runs real Python code: decrypt_aes_gcm(key, corrupted) → raises InvalidTag. verify_ecdsa(alice_pub, sig_orig, corrupted) → raises InvalidSignature. Both exceptions captured and shown.

Attack 3 — Brute Force Login

STRIDE: Elevation of Privilege  The simulator makes 16 real POST /api/login HTTP requests from the browser with wrong passwords. Attempts 1–15 receive 401. Attempt 16 receives 429 Too Many Requests.

sequenceDiagram
    participant ATK as Attacker  (Browser)
    participant RL as Rate Limiter  (sliding deque)
    participant API as Flask  /api/login
    participant BCRYPT as bcrypt  (~150ms/check)
    participant DB as SQLite

    rect rgb(80,20,20)
        Note over ATK,DB: 🔴 ATTACK — 16 rapid POST /api/login requests
        loop Attempts 1 to 15
            ATK->>API: POST {username:"demo_admin", password:"wrong_N"}
            API->>RL: _check_rate_limit("login", attacker_ip, limit=15)
            RL-->>API: ✓ allowed  (N/15 slots used)
            API->>DB: SELECT user WHERE username="demo_admin"
            alt user not found
                API->>BCRYPT: checkpw(dummy, dummy_hash)  ~150ms constant time
                Note over BCRYPT: Prevents username enumeration by timing
            else user found
                API->>BCRYPT: checkpw(wrong_pw, stored_hash)  ~150ms
            end
            API->>API: _append_audit_log("login_failed")
            API-->>ATK: 401 Invalid username or password
        end
    end

    rect rgb(20,60,20)
        Note over ATK,DB: 🛡️ DEFENSE — Rate Limiter blocks on attempt 16
        ATK->>API: POST {username:"demo_admin", password:"wrong_16"}
        API->>RL: _check_rate_limit("login", attacker_ip, limit=15)
        RL-->>API: ✗ BLOCKED  (deque full — 15/15 slots in last 60s)
        API->>API: _append_audit_log("attack_brute_force_blocked")
        API-->>ATK: 429 Too Many Requests  {retry_after: 60}
        Note over ATK: Attacker locked out for 60 seconds
        Note over ATK: At 150ms/guess: 15 guesses × 150ms = 2.25 sec for 15 attempts
        Note over ATK: Without rate limit: 10^6 guesses at 150ms = 41 hours
    end
Attack Speed Without Defense

bcrypt alone limits to ~7 guesses/second/core. An attacker with 10 CPU cores could try 100M passwords in ~160 days — plausible for common passwords.

Rate Limiter (Primary Defense)

15 attempts per 60-second window per IP. After exhausting the window, every attempt returns 429 instantly (no bcrypt called). The sliding window resets naturally after 60s.

bcrypt (Secondary Defense)

Even if the rate limiter is bypassed (e.g., from millions of different IPs in a distributed attack), bcrypt makes each guess ~150ms — 6x slower than SHA-256.

The dashboard makes 16 real HTTP calls from your browser. Each 401 response appears in the Live Feed as a login_failed row. The 429 appears as attack_brute_force_blocked.

Attack 4 — Forged / Expired JWT Token

STRIDE: Spoofing / Elevation of Privilege  Three attack vectors: forge a token with the wrong secret, use a real but expired token, craft a token missing required scopes. All three are tested with real jwt.decode() calls.

sequenceDiagram
    participant ATK as Attacker
    participant API as Flask  verify_token()
    participant JWT as PyJWT  HS256

    rect rgb(80,20,20)
        Note over ATK,JWT: 🔴 VECTOR 1 — Wrong signing secret
        ATK->>ATK: token = jwt.encode({"username":"admin"}, "WRONG_SECRET")
        Note over ATK: Attacker guessed the secret wrong
        ATK->>API: request with forged token
        API->>JWT: jwt.decode(token, REAL_SECRET, algorithms=["HS256"])
        JWT-->>API: ✗ RAISES InvalidSignatureError
        API-->>ATK: 401  "Invalid token"
    end

    rect rgb(80,20,20)
        Note over ATK,JWT: 🔴 VECTOR 2 — Expired token (stolen old token)
        ATK->>ATK: token = jwt.encode({exp: now - 1hour}, REAL_SECRET)
        Note over ATK: Valid signature but expired
        ATK->>API: request with expired token
        API->>JWT: jwt.decode(token, REAL_SECRET, algorithms=["HS256"])
        JWT-->>API: ✗ RAISES ExpiredSignatureError
        API-->>ATK: 401  "Token expired"
    end

    rect rgb(80,20,20)
        Note over ATK,JWT: 🔴 VECTOR 3 — Missing required scope
        ATK->>ATK: token = jwt.encode({scopes:["key:read"]}, REAL_SECRET)
        Note over ATK: Valid token but wrong scopes (no "chat:send")
        ATK->>API: send_message with scoped-down token
        API->>JWT: jwt.decode(token, REAL_SECRET)  → payload OK
        API->>API: payload["scopes"] has "chat:send"?  → NO
        API-->>ATK: 401  "Missing scope: chat:send"
    end

    rect rgb(20,60,20)
        Note over ATK,JWT: 🛡️ SUMMARY — All 3 vectors blocked by verify_token()
        Note over API: verify_token() called on EVERY request and socket event
        Note over API: No way to craft a valid token without the server secret
    end
Why Forgery Is Impossible

JWT uses HMAC-SHA256. Without the server's secret key, any modification to the token's payload changes the signature. The server rejects it immediately.

Token Expiry (60 min TTL)

Even if a token is stolen, it's valid for at most 60 minutes. After expiry, ExpiredSignatureError is raised. The user must re-authenticate.

Scope Enforcement

Every SocketIO event handler uses @require_scope("chat:send"). A valid but scope-limited token (e.g. only key:read) cannot perform chat actions.

Attack 5 — MITM Key Substitution

STRIDE: Spoofing / Information Disclosure  During the key exchange phase, Mallory intercepts Alice's public key and substitutes her own, hoping Bob will encrypt with Mallory's key and Mallory can read the messages.

sequenceDiagram
    participant A as Alice  (Sender)
    participant M as Mallory  (Attacker)
    participant S as Server  (users registry)
    participant B as Bob  (Receiver)

    Note over A,B: ── PHASE 1: Key Registration ──
    A->>S: register(alice_ecdh_pub, alice_ecdsa_pub)
    S->>S: users["alice"] = { alice_ecdh_pub, alice_ecdsa_pub }
    M->>S: register(mallory_ecdh_pub, mallory_ecdsa_pub)
    S->>S: users["mallory"] = { mallory_ecdh_pub, mallory_ecdsa_pub }

    rect rgb(80,20,20)
        Note over M,B: 🔴 ATTACK — Mallory intercepts key exchange
        B->>S: get_public_key("alice")
        Note over M: Mallory intercepts the response
        M->>M: Replaces alice_ecdh_pub with mallory_ecdh_pub
        M-->>B: { mallory_ecdh_pub, alice_ecdsa_pub? }
        Note over B: Bob derives: ECDH(bob_priv, mallory_pub) = wrong_key
        Note over M: Mallory derives: ECDH(mallory_priv, bob_pub) = same_key
    end

    rect rgb(20,60,20)
        Note over M,S: 🛡️ DEFENSE — ECDSA signature bound to registered key
        A->>A: message signed with alice_ecdsa_priv (registered at server)
        A->>S: send_message {ciphertext, sig=ECDSA(alice_priv, envelope)}
        S->>S: alice_registered_key = users["alice"].ecdsa_pub
        S->>S: ECDSA verify(alice_registered_key, sig, envelope)
        S->>S: ✓ Alice's own signature — valid
        S-->>B: receive_message

        Note over M: Mallory cannot forge Alice's ECDSA signature
        M->>S: send_message pretending to be Alice
        S->>S: ECDSA verify(alice_registered_key, mallory_sig, envelope)
        S->>S: ✗ RAISES InvalidSignature!
        Note over S: Mallory's key ≠ Alice's registered key
        S-->>M: delivery_error "Signature verification failed"
    end
MITM Goal

Mallory wants Bob to think he's talking to Alice but actually encrypting to Mallory's key. If successful, Mallory reads all of Bob's messages intended for Alice.

Why ECDSA Defeats It

Alice registered her ECDSA public key at login. The server verifies every message against that registered key. Mallory cannot produce a valid signature for Alice's registered key without Alice's private key.

Real Simulator Code

Generates two real EC keypairs (alice, mallory). Signs with mallory's key. Calls verify_ecdsa(alice_pub, mallory_sig, message) → raises InvalidSignature. Then verifies alice's own sig still passes.

Note on Key Registration

The current system registers keys over an unauthenticated channel (no PKI/CA). In production, key pinning or a Certificate Authority would be needed to fully prevent MITM at the registration step.

Hash Chaining

entry_hash = SHA256(previous_hash + canonical_json_of_event). Changing any character in any historical entry changes its hash, breaking all subsequent links.

ECDSA Signing

Each entry's entry_hash is signed with the server's audit ECDSA private key. Proves the entry was created by this server, not by an attacker who also controls the log file.

SQLite Mirror

Every entry is also written to security_events SQLite table for real-time querying by the dashboard. The NDJSON file is the authoritative tamper-evident record.

Chain Verification

The GET /api/audit endpoint walks the entire chain, verifying each previous_hash matches the prior entry's entry_hash. Returns chain_valid: true/false. Visible in the UI sidebar.

All 8+ Defense Layers — At a Glance

Every layer is active and enforced on every request. The defense-in-depth principle means an attacker must defeat multiple independent mechanisms.

① AES-256-GCM Encryption

AEAD cipher — one operation gives both confidentiality and integrity. 16-byte auth tag detects any ciphertext modification.

AESGCM(key).decrypt(iv, ct, aad) → raises InvalidTag

② ECDH P-256 Key Exchange (PFS)

Ephemeral keys generated fresh each session. Shared AES key is derived locally — never transmitted. Perfect Forward Secrecy.

shared = ECDH(alice_priv, bob_pub) → HKDF-SHA256

③ ECDSA P-256 Digital Signatures

Every message envelope is signed. Server verifies against the sender's registered public key before forwarding. Prevents tampering and MITM.

verify_ecdsa(registered_pub, sig, envelope) → InvalidSignature

④ SHA-256 Plaintext Hash

Computed before encryption, verified after decryption. Provides a third independent integrity check at the plaintext level.

SHA256(plaintext) === data.hash → or reject

⑤ JWT Authentication + Scopes

HS256-signed tokens with 60-min TTL and per-action scopes. Every API and socket event verifies the token before acting.

jwt.decode(token, SECRET) → InvalidTokenError / ExpiredSignatureError

⑥ Sliding-Window Rate Limiter

Per-IP login: 15/60s. Per-user messages: 120/60s. Per-IP connections: 40/60s. Returns HTTP 429 with retry-after seconds.

_check_rate_limit(action, subject, limit) → False, retry

⑦ bcrypt Password Hashing

Cost factor 12 (~150ms/check). Per-password random salt defeats rainbow tables. Dummy check for non-existent users prevents timing-based enumeration.

bcrypt.hashpw(pw, gensalt(rounds=12)) → 60-byte hash

⑧ Hash-Chained Audit Log

Every event SHA-256 chained to the previous. Each entry ECDSA-signed. Append-only file. Chain validity displayed in UI.

entry_hash = SHA256(prev_hash + event_json)

⑨ Server-Side Replay Deduplication

In-memory seen_message_ids set tracks all (sender, msgId) pairs. Duplicate emits delivery_error and logs attack_replay_blocked.

if msg_key in seen_message_ids: → reject + log

⑩ Scapy SYN/ACK Network Monitor

Captures raw TCP packets on host interfaces. SYN/ACK ratio > 3.0 → dos_suspected=1 → InfluxDB → Grafana visual alert.

ratio = syn_count / max(ack_count, 1) → if ≥ 3.0: alert
